## 1. Overview & Security Objectives

In compliance with Task 2 of Phase 22.1, GRICC database backup operations have been upgraded from unencrypted plaintext SQLite files to authenticated, symmetric encryption using **AES-256-GCM** (Galois/Counter Mode).

### Core Requirements Satisfied:
1. **Authenticated Encryption:** AES-256-GCM provides both confidentiality and data integrity/authenticity (preventing tampering or bit-flipping attacks).
2. **Key Derivation:** Scrypt key derivation function (KDF) with high work factors and random per-backup 16-byte salt to resist brute-force/dictionary attacks.
3. **Environment-Driven Configuration:** Keys are retrieved exclusively via `BACKUP_ENCRYPTION_KEY` or `--key` CLI arguments. Zero hardcoded secrets in source control.
4. **Backward Compatibility & Automatic Format Detection:** Plaintext `.db` backups remain restorable; encrypted `.db.enc` backups are automatically detected via magic byte identification and decrypted during restoration.
5. **Fail-Safe Integrity Verification:** Decrypted databases must pass SQLite `PRAGMA integrity_check` before being swapped into production, and temporary plaintext buffers are securely scrubbed.

## 2. Cryptographic Architecture

### 2.1 Binary Container Format (`.db.enc`)

Every encrypted backup generated by `server/scripts/backup-database.js` adheres to a strict 53-byte binary header followed by the AES-256-GCM ciphertext payload:

```
+-------------------+-----------------+----------------+-----------------+-------------------------+
| Magic Bytes (8 B) | KDF Salt (16 B) | GCM IV (12 B)  | Auth Tag (16 B) | Ciphertext Payload (N B)|
+-------------------+-----------------+----------------+-----------------+-------------------------+
```

| Component | Size | Specification | Purpose |
| :--- | :--- | :--- | :--- |
| **Magic Header** | 8 bytes | ASCII `'GRICCBKP'` (`0x47 0x52 0x49 0x43 0x43 0x42 0x4B 0x50`) | File type identification and format validation |
| **KDF Salt** | 16 bytes | `crypto.randomBytes(16)` | Salt for Scrypt key derivation, unique per backup |
| **Initialization Vector (IV)** | 12 bytes | `crypto.randomBytes(12)` | Standard NIST SP 800-38D GCM nonce |
| **Authentication Tag** | 16 bytes | `cipher.getAuthTag()` | Cryptographic MAC for tamper verification |
| **Ciphertext Payload** | Variable | AES-256-GCM encrypted SQLite binary buffer | Protected database content |

### 2.2 Key Derivation Function (KDF)

Key derivation utilizes Node.js native `crypto.scryptSync`:
- **Password:** UTF-8 passphrase from `process.env.BACKUP_ENCRYPTION_KEY`
- **Salt:** 16 cryptographically random bytes
- **Key Length:** 32 bytes (256 bits)
- **Cost Parameters:** `N=16384`, `r=8`, `p=1` (standard memory-hard parameters)

## 3. Implementation Details

Located in `server/scripts/backup-database.js`:

```javascript
// Encryption logic
function encryptBackupBuffer(plainBuffer, encryptionKey) {
  const salt = crypto.randomBytes(KDF_SALT_LENGTH);
  const derivedKey = crypto.scryptSync(encryptionKey, salt, 32);
  const iv = crypto.randomBytes(GCM_IV_LENGTH);
  const cipher = crypto.createCipheriv('aes-256-gcm', derivedKey, iv);
  
  const ciphertext = Buffer.concat([cipher.update(plainBuffer), cipher.final()]);
  const tag = cipher.getAuthTag();
  
  return Buffer.concat([
    Buffer.from(MAGIC_HEADER, 'ascii'),
    salt,
    iv,
    tag,
    ciphertext
  ]);
}
```

### 3.1 Decryption & Authentication Verification

If an incorrect encryption key is provided or if the ciphertext/tag has been modified in transit, Node.js `crypto` immediately throws:
```
Error: Unsupported state or unable to authenticate data
```
The script catches this error and cleanly aborts restoration without altering the target database.

## 4. Operational CLI Usage

### 4.1 Creating an Encrypted Backup

Using environment variable:
```bash
export BACKUP_ENCRYPTION_KEY="Production-Grade-Passphrase-32+Chars!"
node server/scripts/backup-database.js --backup
```

Or using explicit parameter flag:
```bash
node server/scripts/backup-database.js --backup --key="Production-Grade-Passphrase-32+Chars!"
```

**Output:**
```
[2026-11-13T05:44:58.989Z] [BACKUP] Created encrypted backup: server/backups/gricc-backup-2026-11-13T05-44-58-989Z.db.enc (284.5 KB)
```

### 4.2 Restoring from an Encrypted Backup

```bash
node server/scripts/backup-database.js --restore="server/backups/gricc-backup-2026-11-13T05-44-58-989Z.db.enc" --key="Production-Grade-Passphrase-32+Chars!"
```

**Restoration Process Steps:**
1. Verifies the file begins with `GRICCBKP`.
2. Extracts salt, IV, tag, and ciphertext.
3. Derives key via Scrypt and attempts authenticated decryption.
4. Writes temporary decrypted buffer to an atomic `.tmp.db` file.
5. Runs `PRAGMA integrity_check` on the decrypted database.
6. Queries table counts to ensure core schemas (`users`, `incidents`, `audit_logs`) are intact.
7. Atomically replaces target database (`server/data/gricc.db`).
8. Securely deletes temporary `.tmp.db`.
